Regulatory Wiki

A regulatory-intelligence system for Indian regulators. It watches regulators' websites every day, collects every new circular, order, notification and report, uses an AI model to tag each one against a regulator-specific taxonomy, and publishes the result as a searchable, structured library.

Overview

Every regulator publishes its rules on its own website, each organised differently. This system visits those websites automatically, picks up anything new, reads it, labels it (what kind of document it is, what subject it covers, whether it is still in force), and files it in one place where lawyers can browse and filter it. Anything the AI isn't sure about is set aside for a person to check before it goes live.

The system has five layers, each in its own part of the codebase:

1. Scrapers & watchers

One per regulator, in scrapers/. They visit the regulator's site and list every document with its title, date and file link.

2. Adapters

Convert each scraper's regulator-specific output into one shared format, the normalized document.

3. Sync & ingest

lib/sync.ts runs everything daily; lib/ingest.ts drops documents already stored and has DeepSeek classify the new ones.

4. Database

PostgreSQL via Prisma. It stores the taxonomies, the documents, their classifications, and a log of every sync run.

5. Website

A Next.js app with a public library (ANS), a human review queue for admins, and the gyaani / Horizon Scan product shell.

Step by step

  1. Scrape. The watcher for each regulator loads its listing pages and records every document: title, date, category, and the link to the file. Sites that need a real browser (JavaScript-rendered pages, bot protection) use Playwright with Chromium. Simpler sites use plain HTTP requests (Python requests, or fetch + cheerio for the TypeScript scrapers).
  2. Normalize. The adapter maps that raw output onto the shared NormalizedDocument contract (scrapers/normalized_document.py): regulator_code, source_id, title, source_url, published_date, file_url, category_hint, status_hint, raw_text, needs_download, scraped_at. It writes one JSON file per regulator, e.g. scrapers/data/mib_normalized.json.
  3. Deduplicate. Every document has a stable source_id, a hash the scraper computes from things that don't change (usually the regulator, the document's URL and its title). The sync compares these against what Postgres already holds and keeps only the genuinely new ones.
  4. Classify. For each new document, lib/ingest.ts downloads the file where needed, extracts the text (PDF parsing, with OCR for scanned files in CCI, FIU and DST), and asks DeepSeek (deepseek-chat) to pick tags from that regulator's own taxonomy, which comes from Postgres with each tag's definition.
  5. Publish or queue. Results with confidence of at least 0.75 and no warning signs publish straight away. Everything else is flagged for the admin review queue at /admin/review.
  6. Record. Every sync writes a SyncRun row, plus one SyncRunRegulator row per regulator: status (OK, BLOCKED, ERROR, SKIPPED), rows scraped, new, ingested, flagged, errors and duration.

Notes per regulator

DoT

dot.gov.in is the most demanding site. It is JavaScript-rendered, many listing rows are "topic pages" hiding dozens of sub-documents (one holds 115+), and it rate-limits in bursts. The watcher expands every topic page, retries blocked pages after 1- and 3-minute pauses, and records any section it couldn't reach. A full crawl takes 60–75 minutes, so DoT has its own 90-minute limit and runs last. Under the sync it runs in daily mode, stopping on each topic page at the first document the wiki already has.

EPFO, ESIC, CLC (labour)

These share one stack. labour_scrape.py fetches pages with generic WAF/block detection (is_blocked()), labour_parser.py has one parser per source, and labour_watcher_common.py drives them and writes the CSV. labour_adapter.py serves all three.

CCI and FIU

Standalone Python packages with their own config, SQLite database, downloader, text extractor with OCR fallback (Poppler + Tesseract) for scanned pre-2015 orders, and their own classifier. The run_*_scrape.py bridges run each package's scrape command; the adapters export the SQLite rows to the shared JSON format. Documents already in the wiki are skipped before anything is downloaded.

MERC

MERC exposes its orders, daily orders and hearings through the site's own AJAX data feeds, about 20,800 documents in three requests. The database holds a 100-document taxonomy sample. The full backfill is deliberately a one-off manual run (skipScheduled in lib/sync.ts), so a routine nightly job never turns into a 20,000-document classification bill.

Saral Sanchar and DST

Written in TypeScript because these sites need no browser automation. Each watch.ts writes normalized JSON directly, so there is no adapter step. DST fans out across four source clusters and extracts document text itself, with OCR as the fallback.

DOS-ISRO

Three sources in one watcher: ISRO (press releases, tenders, reports, policy), NSIL (tenders, reports) and IN-SPACe (authorizations, data disseminators, events, opportunities, publications, the national geospatial policy), the last via its ServiceNow page API. Some IN-SPACe records are table rows with no file of their own; the website explains this in the document preview.

Adding one to the daily sync takes three steps:

  1. Seed the regulator's taxonomy: add a prisma/seed-<code>.ts, following the existing ones.
  2. Add a run_<code>_adapter.py that writes scrapers/data/<code>_normalized.json.
  3. Add an entry to REGULATORS in lib/sync.ts, with its block markers.

One PostgreSQL database holds everything the website shows: the list of regulators, each regulator's labels, every collected document, the labels chosen for it, and the history of every daily run.

Classification & human review

The AI reads each new document alongside the regulator's list of possible labels and their definitions, then picks the best fit and says how sure it is. Confident answers go straight into the library; uncertain ones wait for a person.
  • Model: DeepSeek deepseek-chat, called through the OpenAI SDK pointed at DeepSeek's compatible endpoint (lib/ingest.ts).
  • Prompt: built per regulator from Postgres: every Subject, Instrument Type and Status tag, with its definition, plus the scraper's category hint and whether the text is present, missing, or failed to extract.
  • Rules: one Subject tag, with fallback to its parent; entity-versus-activity tie-breaks; Amended, Superseded and litigation statuses only when the document itself says so; In Force by default.
  • Auto-accept threshold: 0.75. Below that, or when a check trips (low confidence, unreadable date, failed text extraction), the entry is flagged. About 83% of the 8,375 documents were accepted automatically.
  • Review: admins sign in at /admin/login and work through /admin/review, confirming or correcting tags per document.

The live corpus. Browse by regulator, domain, subject or instrument type; filter the document list; open a document to see its tags, the classifier's reasoning and an inline preview. PDFs go through our own proxy (/api/documents/[id]/file) because several regulators block embedding. Dates later than today get an "unverified date" badge rather than being silently corrected.

Daily automation

.github/workflows/daily-sync.yml runs every day at 03:00 UTC (about 08:30 IST), and can also be started by hand from the Actions tab (Run workflow). It:

  1. installs Node and Python dependencies (the slim requirements-sync.txt, plus the CCI and FIU package requirements);
  2. installs Playwright Chromium, Poppler and Tesseract;
  3. generates the Prisma client;
  4. runs xvfb-run -a npx tsx scripts/sync-all.ts --trigger schedule (xvfb provides a virtual display for DoT's headed browser);
  5. prints recent sync history with scripts/show-sync-runs.ts.

A regulator that is blocked or fails is recorded and the run moves on to the next one. The job only fails if every regulator errors. MERC is skipped on scheduled runs until its one-off backfill is done.

Timings measured on 24 September 2026: ten regulators end to end in 16 minutes (CCI about 1 minute, FIU about 20 seconds, MIB about 2.5 minutes, ESIC about 6 minutes); DoT 60–75 minutes on its own. The job budget is 150 minutes.

Reliability safeguards built in

Government websites change layout, rate-limit, time out and go down. The pipeline is built to report that honestly and recover on the next run, instead of silently recording "nothing new".

Knows what it already has

Before each regulator runs, the sync writes the source_ids already in Postgres to a file named in SYNC_KNOWN_SOURCE_IDS_FILE. CCI, FIU, DST and DoT skip those documents before any download, OCR or AI call. That keeps each run fast and costs proportional to what's new, even on a fresh CI machine with no local state.

Never mistakes "empty" for "nothing new"

If a watcher finds zero documents across every source, it exits with an error and leaves the previous output untouched. The run is then recorded as ERROR or BLOCKED, never as a confident "0 new documents".

Block detection

Watchers print standard markers when a site refuses them (HTTP 401, 403 or 429, WAF signatures). The sync records which regulators were blocked and still ingests whatever did come back.

Stable document IDs

IDs are built from things that don't move: for paginated feeds, the feed URL (never the page number) plus the title and file; for MIB, a canonical form of each link. A document that moves around a listing is still recognised.

Readable logs

The last 15 lines of every scraper's and adapter's output go into the sync log, so a CI failure can be diagnosed from the Actions log alone.

Patient, bounded retries

Slow sites get retries with longer timeouts. DST's shared fetch has a circuit breaker, so a site that's really down costs minutes, not the whole job. Every scraper also runs under a per-regulator time limit.

Honest dates

A future date (a scheduled hearing or event) is never stored as a publication date, month-only dates are stored consistently on every machine, and any genuinely future date from a source is shown with an "unverified" badge.

Verification tool

python scrapers/verify_normalized.py <json> checks any scraper's output: required fields, duplicate IDs, date format, future dates, and a random sample of links that must really download (a PDF must actually be a PDF).

Running it yourself

First-time setup

git clone <repository URL> && cd regulatory-wiki
cp .env.example .env              # then fill in your own values (see Credentials)
npm install
npx prisma generate
npx prisma migrate deploy         # create the schema in your database
npx tsx prisma/seed-dot.ts        # …and the other prisma/seed-*.ts files (see README)
npx tsx scripts/set-admin-password.ts you@firm.com 'a-strong-password' 'Your Name'

# Python side (for the scrapers)
pip install -r scrapers/requirements-sync.txt
pip install -r scrapers/cci_scraper/requirements.txt
pip install -r scrapers/fiu_scraper/requirements.txt
python -m playwright install --with-deps chromium

Poppler and Tesseract must be on PATH for the OCR fallbacks. If you're pointing at an existing, already-populated database, skip the migrate and seed steps.

Everyday commands

npm run dev                                        # website on http://localhost:3000
npm run sync                                       # sync every regulator
npx tsx scripts/sync-all.ts --only CLC,ESIC        # sync specific regulators
npm run sync:runs                                  # recent sync history

# run one scraper by hand (from scrapers/)
python labour_watcher_clc.py && python run_clc_adapter.py
npx tsx saral-sanchar/watch.ts
python verify_normalized.py data/clc_normalized.json

Credentials & access

No passwords, API keys or database addresses are stored in the code. The repository only contains blank templates. Each person or server running the system supplies its own values, in a private settings file on their machine and in GitHub's encrypted secrets store.

Every tracked file and the full Git history were checked for the DeepSeek key, the database connection details and the login secret, and none of them appear. Personal file paths and account names were removed from code comments and logs. These values need to be supplied:

Handover checklist

  1. Repository access: add the team as collaborators, or transfer the repository to the team's GitHub organisation (Settings → General → Transfer ownership).
  2. GitHub secrets: under Settings → Secrets and variables → Actions, overwrite DATABASE_URL and DEEPSEEK_API_KEY with the team's own values. Secrets don't carry over when a repository is transferred, so after a transfer they must be added fresh.
  3. Database: either transfer or share the existing Neon project (keeps all 8,375 classified documents), or create a new database and populate it with migrate deploy, the seed scripts, and a sync.
  4. Admin logins: create accounts for each reviewer with set-admin-password.ts.
  5. Local .env: each developer copies .env.example and fills in the values above.

Recommended next steps

The pipeline is complete and verified end to end. These are the items to pick up next, in rough priority order.

1. Run the daily job from an Indian connection

Some Indian government sites treat GitHub's US-based servers differently from Indian connections. EPFO, for example, answers GitHub with HTTP 403 but serves every page to an Indian connection. The workflow is ready for this: register a self-hosted GitHub Actions runner on an Indian machine or cloud VM (Linux, with passwordless sudo for the package steps, or the packages preinstalled), then set the repository variable SYNC_RUNNER to its label. No code changes needed. Until then, affected regulators are recorded clearly as BLOCKED in the run log.

2. Tidy earlier duplicates

The causes of the duplicate entries have been fixed, so no new ones are being created. Copies stored before the fix are kept in place until the team decides to remove them, because removal deletes their entries:

  • Saral Sanchar: 242 older copies. Remove with npx tsx scripts/rekey-saral-sanchar.ts --apply --delete-duplicates (dry-run first without the flags).
  • MIB: 19 older copies, from the site alternating between two forms of the same link. A small cleanup script along the same lines would handle them.

3. Complete the DoT catch-up

dot.gov.in publishes considerably more than the 592 documents currently stored, and recent crawls surfaced several hundred more. The next successful DoT run will catch these up in one go (a larger than usual batch of classifications). It runs last in the sync, so it never delays the other regulators. Running it once by hand gives the most control:

npx tsx scripts/sync-all.ts --only DOT

DoT also re-uploaded its 2025-26 Annual Report chapters under new file addresses, so those 13 chapters will appear as new documents alongside the earlier versions.

4. Run the MERC backfill

MERC's scraper and taxonomy are ready, and about 20,800 documents are available. Run the one-off backfill deliberately, then remove MERC's skipScheduled flag in lib/sync.ts so it joins the daily sync:

npx tsx scripts/sync-all.ts --only MERC

5. Smaller follow-ups

  • DST: dst.gov.in's call-for-proposals archive is sometimes very slow to respond. On those days the run skips it cleanly and picks it up on a later day, and nothing already stored is affected.
  • CLC: the Chief Labour Commissioner relaunched its website in September 2026 and is still republishing content. The scraper follows the new site; 47 older documents point to pages the old site no longer serves, and can be re-pointed with remap-moved-documents.ts as the new site fills in.
